# Github Auth 初始化、快速解锁与备份设计

日期：2026-08-15

## 1. 目标

本次改造在现有 Tauri 2 + React 桌面应用中完成以下能力：

1. 将初始化面板固定在窗口中央，拆分为“设置主密码”和“选择登录方式”两个稳定尺寸的步骤。
2. 初始化时允许选择“仅使用密码登录”或“添加 2FA 快速登录”。
3. 选择 2FA 后显示 Google Authenticator 二维码，并在验证码验证成功后才启用。
4. 启用 2FA 快速登录后，登录页默认使用 6 位验证码，同时允许切换回主密码。
5. 增加手动备份、运行期间自动备份、备份目录选择、备份轮换和加密备份导入。
6. 导入支持追加、替换、加入单一备份分组三种模式，并严格区分备份密码与当前主密码。
7. 将加密、认证、迁移和文件写入集中到 Rust 安全内核，兼容现有 `version: 1` 数据。

## 2. 非目标与安全边界

- 2FA 快速登录是绑定当前 Windows 用户和当前设备的便捷解锁方式，不是可跨设备使用的第二个解密密码。
- 单独的 6 位 TOTP 只有约 20 位熵，不能直接作为离线文件加密密钥。其安全性必须依赖 Windows DPAPI、当前 Windows 登录边界和失败冷却。
- 主密码始终可独立解锁保管库，并是跨设备解密备份的唯一凭据。
- 备份不要求启用 2FA，2FA 登录绑定也不写入备份。
- GitHub 账户条目自身保存的 TOTP 密钥属于保管库业务数据，会随完整备份一同加密保存。它与用于解锁 Github Auth 的 2FA 密钥是两个不同概念。
- `.ghauth-backup` 是本软件严格识别的专用格式，但无法从密码学上阻止第三方开发兼容工具。安全保证是没有正确密码就无法读取或篡改备份内容。
- 自动备份只在应用进程运行期间执行，不安装 Windows 后台服务或计划任务。
- 本次不增加云同步、远程恢复或在线账户体系。

## 3. 总体架构

### 3.1 React 展示层

React 负责：

- 初始化、解锁、设置、二维码和导入向导的界面状态。
- 收集密码和验证码，并通过受限的 Tauri command 传递给 Rust。
- 展示已经解密的保管库内容。
- 在锁定、退出或认证失败后清空表单和解密后的 React 状态。

React 不再负责：

- 密码派生和保管库加解密。
- 备份文件解析、目录写入或原子替换。
- TOTP 密钥生成、验证码验证或失败次数判断。

### 3.2 Rust 安全内核

Rust 负责：

- Argon2id 密码派生、随机数据密钥生成和 AES-256-GCM 加解密。
- 当前会话的数据密钥管理与锁定清理。
- Google Authenticator 兼容 TOTP 的生成、二维码准备和验证。
- Windows DPAPI 快速解锁材料的保护与读取。
- 主保管库、备份文件和非敏感备份设置的严格解析。
- 手动备份、自动备份轮换、导入、迁移和原子写盘。

敏感字节缓冲区使用 `zeroize` 清理。生产日志不得包含密码、TOTP 密钥、数据密钥、账户密码、邮箱或解密后的载荷。

## 4. 加密格式

### 4.1 保管库 v2

新版保管库使用一个随机 32 字节数据密钥加密完整 `VaultPayload`。主密码不直接加密业务数据，而是派生密钥后包裹数据密钥。

逻辑结构如下：

```text
VaultEnvelopeV2
  format: "github-auth-vault"
  version: 2
  vaultId: random UUID
  kdf:
    algorithm: "argon2id"
    memoryKiB: 65536
    iterations: 3
    parallelism: 1
    salt: random 16+ bytes
  passwordKeyWrap:
    nonce: random 12 bytes
    ciphertext: AES-256-GCM(dataKey)
  payload:
    nonce: random 12 bytes
    ciphertext: AES-256-GCM(serialized VaultPayload)
  updatedAt: ISO-8601 timestamp
```

约束：

- Argon2id 默认参数为 64 MiB、3 次迭代、并行度 1、32 字节输出。
- 导入时只接受安全且有上限的 KDF 参数，避免恶意文件触发过量内存或 CPU 消耗。
- 数据密钥、密码包裹和载荷使用独立的 nonce 与用途固定的 AAD。
- 每次保存载荷都生成新的随机 nonce。
- 更改主密码只重新派生密码密钥并重新包裹同一数据密钥，不需要解密后逐字段重写业务数据。
- JSON 使用严格 schema，拒绝未知字段、无效 Base64、错误长度、超限文件和不支持的版本。

### 4.2 旧版 v1 迁移

现有 v1 文件继续可读。Rust 使用与旧实现一致的 PBKDF2-SHA-256、310,000 次迭代和 AES-256-GCM 验证旧主密码。

迁移顺序：

1. 使用用户输入的旧主密码完整解密并校验 v1 载荷。
2. 生成新的 v2 数据密钥、Argon2id 盐和所有 nonce。
3. 将 v2 写入同目录临时文件并同步到磁盘。
4. 重新读取临时文件并验证可解密性。
5. 原子替换主文件。
6. 任一步失败都保留原 v1 文件，并向用户显示可重试错误。

## 5. 初始化与登录

### 5.1 居中初始化

初始化页保留现有深色视觉语言，但主内容改为水平和垂直居中。面板使用固定宽度和响应式最大宽度，在桌面与窄屏中保持稳定，不因步骤内容变化发生横向位移。

步骤 1：设置主密码

- 输入主密码和确认密码。
- 保留至少 12 个字符的现有下限。
- 前端做即时一致性检查，Rust 再做最终长度和大小校验。
- 提交后由 Rust 创建内存中的待完成保管库，不立即写入最终文件。
- React 随即清空两个密码输入框。

步骤 2：选择登录方式

- 左侧选项为“仅使用密码登录”。选择后 Rust 提交待完成保管库。
- 右侧选项为“添加 2FA 快速登录”。选择后进入二维码弹窗。

### 5.2 Google Authenticator 绑定

Rust 生成 160 位随机 TOTP 密钥，使用标准 `otpauth://totp/...` 参数：SHA-1、6 位、30 秒周期。密钥在绑定确认前只存在于 Rust 待完成会话。

二维码弹窗包含：

- Google Authenticator 可扫描的二维码。
- 6 位验证码输入框。
- “验证并完成初始化”主操作。
- “返回，仅使用密码”次操作。
- 无法扫描时可显式展开并复制手动设置密钥。

只有当前验证码验证成功后，Rust 才提交保管库和 DPAPI 快速解锁材料。关闭应用、取消或验证失败不会留下半启用状态。

### 5.3 验证码快速解锁

DPAPI sidecar 绑定 `vaultId`，并以 Windows current-user scope 保护以下材料：

- 快速解锁 TOTP 密钥。
- 当前保管库数据密钥。
- 最近一次成功使用的 TOTP 时间步。
- 快速解锁失败与冷却状态。

解锁流程：

1. 存在有效 DPAPI sidecar 时，登录页默认显示验证码快速解锁。
2. 用户输入当前 6 位验证码，Rust 解开 sidecar、检查 `vaultId`、验证时间窗和重放状态。
3. 验证成功后，Rust 使用数据密钥解密主保管库，并更新最近使用的时间步。
4. 登录页始终提供“改用主密码”，主密码可独立完成解锁。

验证码允许有限的前后时间漂移，但同一个时间步的验证码不能重复用于成功解锁。失败达到阈值后进入递增冷却，初始 30 秒，最高 15 分钟。该限制用于降低应用内猜测风险，不宣称能抵抗已经控制当前 Windows 用户会话的攻击者。

通过主密码解锁后，设置页允许重新绑定或停用快速解锁。重新绑定和停用均要求再次验证当前主密码。丢失 Authenticator 不影响主密码登录和备份恢复。

### 5.4 会话锁定

锁定时：

- Rust 清除内存中的数据密钥和解密载荷。
- React 清空账户数据、搜索、上下文菜单、密码和验证码状态。
- 自动备份仍可复制已经落盘的加密主文件，因为它不需要解密数据。

## 6. 备份

### 6.1 备份文件

备份使用 `.ghauth-backup` 扩展名，逻辑结构如下：

```text
BackupContainer
  format: "github-auth-backup"
  version: 1
  createdAt: ISO-8601 timestamp
  appVersion: producing application version
  vault: complete VaultEnvelopeV2
```

外层只包含格式、版本和时间等非敏感元数据。账户、分组、应用偏好、账户密码和账户 TOTP 密钥全部位于认证加密的载荷中。备份密码就是生成该快照时主保管库使用的主密码。

当主密码以后发生变化，旧备份仍使用旧密码，新备份使用新密码。这一行为需要在更改密码成功提示中明确说明。

### 6.2 手动备份

- “立即备份”打开原生保存对话框。
- 默认目录为自动备份目录，默认文件名包含本地日期和时间。
- Rust 从当前已验证的加密主文件生成备份，不在 React 中拼装或下载 Blob。
- 写入成功后重新读取并验证容器结构和内层认证数据，再提示成功。

### 6.3 自动备份

默认设置：

- 默认目录：`%LOCALAPPDATA%\com.githubauth.vault\backups`。
- 默认频率：每天一次。
- 默认保留：最近 10 份。
- 只在应用运行期间执行，锁定状态也可执行。

用户可以：

- 开启或关闭自动备份。
- 从每 6 小时、每 12 小时、每天、每周中选择频率。
- 使用原生目录选择器指定目录。
- 将保留数量调整为 1 到 100。

备份调度、目录和保留数量不属于账户机密，保存在 Rust 管理的独立非敏感设置文件中，以便应用处于锁定状态时继续调度。

自动备份流程：

1. 定期检查是否到达下次执行时间。
2. 验证主保管库结构后写入唯一时间戳临时文件。
3. 同步并重新验证临时备份。
4. 原子改名为最终 `.ghauth-backup` 文件。
5. 只有新备份成功后才按创建时间删除超出保留数量的最旧自动备份。

手动备份和替换前备份不纳入自动轮换删除范围。

## 7. 导入

导入只能在当前保管库已经解锁后开始。

### 7.1 文件验证与备份密码

1. 使用原生文件选择器选择 `.ghauth-backup`。
2. Rust 校验文件大小、专用格式、版本、字段和 KDF 参数范围。
3. 界面要求输入“备份生成时的主密码”。
4. Rust 使用该密码解开备份数据密钥并验证 AES-GCM 认证标签。
5. 密码错误和文件损坏统一显示“备份密码错误或文件已损坏”，避免泄露额外判断信息。
6. 成功后只返回账户数、分组数、创建时间等摘要，等待用户选择导入模式。

备份密码只用于本次读取，完成、取消或失败后立即清理，不会替换当前主密码。

### 7.2 模式 1：添加到当前数据

- 保留当前账户、分组和所有当前设置。
- 为导入的账户与分组生成新 ID，避免与当前数据冲突。
- 重建账户到导入分组的 ID 映射。
- 重名分组追加“（导入）”后缀；仍冲突时追加递增编号。
- 不根据名称、邮箱或密码自动覆盖、合并或删除账户。
- 最终组合载荷使用当前保管库数据密钥重新加密保存。

### 7.3 模式 2：替换当前数据

选择替换后先询问“是否备份当前数据”：

- 选择“是”时，在配置的自动备份目录中创建不受轮换管理的“替换前”手动备份。备份失败则中止替换。
- 选择“否”时跳过备份。
- 无论选择“是”或“否”，下一步都必须输入当前客户端主密码。

两个密码的职责必须分别标注：

- 备份密码：读取导入文件。
- 当前主密码：授权破坏性替换，并验证当前密码包裹。

替换结果：

- 账户、分组、语言和剪贴板偏好由备份载荷替换。
- 当前主密码保持不变。
- 当前 Github Auth 快速解锁 TOTP/DPAPI 绑定保持不变。
- 当前自动备份目录、频率和保留数量保持不变。
- 导入载荷使用当前保管库的数据密钥和密码包裹重新保存。

### 7.4 模式 3：加入一个备份分类

- 新建分组“备份导入 · YYYY-MM-DD”；重名时追加时间或编号。
- 为所有导入账户生成新 ID，并全部归入该单一分组。
- 忽略备份中的原分组结构、语言、剪贴板和自动备份设置。
- 保留当前账户、分组和设置。
- 最终载荷使用当前保管库数据密钥重新加密保存。

### 7.5 原子提交与回滚

三种模式都先在内存中构建完整目标载荷，并执行 schema 与引用完整性检查。写入时使用临时文件、磁盘同步、重新读取验证和原子替换。任何失败都不得修改当前主文件或 DPAPI sidecar。

## 8. UI 结构

### 8.1 初始化与登录页

- 初始化框在可用视口中水平、垂直居中。
- 固定面板尺寸使用响应式 `width`、`max-width` 和稳定的内部网格，步骤切换不改变页面布局。
- 第二步的两个选项在桌面端左右排列，窄屏改为上下排列。
- 选择右侧后使用模态框展示二维码和验证码输入，不把二维码作为页面装饰。
- 启用快速解锁后默认聚焦验证码输入；主密码切换使用清晰的分段控件或文本命令。

### 8.2 设置页

安全区包含：

- 更改主密码。
- 2FA 快速解锁状态、重新绑定和停用。

备份区包含：

- 自动备份开关。
- 频率、目录和保留数量控件。
- 上次成功时间、下次计划时间和最近错误状态。
- “立即备份”和“导入备份”命令。

### 8.3 导入向导

导入使用分步对话框：

1. 选择文件并输入备份密码。
2. 展示备份摘要。
3. 选择三种导入模式。
4. 替换模式显示备份当前数据确认和当前主密码验证。
5. 显示结果摘要或可重试错误。

按钮和输入框在所有支持的窗口尺寸下必须完整显示，不允许文字重叠或对话框超出视口。

## 9. Tauri 接口边界

Tauri command 按用途拆分，不提供任意路径读写接口。建议接口族：

- 初始化：开始初始化、开始 TOTP 设置、确认 TOTP、完成密码模式、取消初始化。
- 解锁：密码解锁、TOTP 解锁、锁定、读取已解锁载荷。
- 保存：保存已解锁载荷、更改主密码。
- 2FA：读取状态、开始重新绑定、确认重新绑定、停用。
- 备份：读取/保存备份设置、选择目录、手动备份、读取导入摘要、提交导入。

每个接口限制字符串长度、文件大小、枚举值和状态转换。文件 token 或 Rust 内存中的导入会话用于连接“摘要”和“提交”步骤，React 不持有已解密的备份密码或备用数据密钥。

## 10. 错误处理

- 密码、验证码和篡改错误使用不泄露内部结构的用户文案。
- 目录不存在时尝试创建；无权限、磁盘满或路径失效时保留当前数据并显示具体可操作错误。
- 自动备份失败不阻止正常保存保管库，并在设置页保留最近错误；下一周期继续重试。
- DPAPI sidecar 缺失、损坏或 `vaultId` 不匹配时禁用快速解锁入口，但主密码登录保持可用。
- 系统时间明显异常时提示校准时间，并允许切换主密码。
- 应用崩溃后启动时只恢复经过完整校验的主文件；临时文件不直接成为有效数据源。
- 备份和主保管库均保留 10 MiB 默认大小上限；若未来提高上限，必须同时更新 Rust 和测试。

- 使用不同备份密码执行三种导入模式。
- 模拟损坏文件、错误密码、不可写目录和替换中断，确认当前数据不丢失。
- 在桌面最小尺寸和窄屏尺寸检查初始化、二维码和导入对话框无重叠。

## 12. 完成标准

- 初始化框居中且两步切换稳定。
- Google Authenticator 绑定必须经过验证码确认。
